# 1. Introduction

## 1.1 Purpose

This SRS defines the verifiable requirements for an AI-assisted platform that teaches software engineering through real work on the student's own computer. It is the normative baseline for design, implementation, testing and acceptance.

## 1.2 Product scope

The long-term product has three learning modes:

1. **Build (Mode 1):** build a project from scratch through a guided lab.
2. **Debug (Mode 2):** fix a known bug in an existing codebase with AI help and tests.
3. **Contribute (Mode 3):** practise a Git/GitHub pull-request workflow in a platform-controlled repository.

The product is delivered in releases (Section 1.4). **Only the MVP release is committed for the first pilot.** Later releases are specified so the architecture can accommodate them, but they are not a commitment until the MVP pilot is evaluated.

### In scope (MVP)

- Sign-in with Google; minimal private student profile.
- Catalogue of Python labs delivered as immutable, versioned lab bundles.
- Environment detection and consented setup for Python tooling (Python, `uv`, Git guidance).
- Guided lab experience: steps, explanations, copyable snippets, per-step checks.
- Code workspace with terminal and local test execution.
- Text AI tutor through a backend proxy with context controls and redaction.
- **Practice** results (computed locally, unverified) and **Verified** results (graded on a server-side sandbox).
- Progress saved locally and synchronised to the cloud.
- Content authored as files in a version-controlled repository and published by CI.

### Out of scope for the MVP (deferred, see Section 5.14)

Admin web portal; local LLM/Ollama fallback and hardware profiling; leaderboards and achievements; voice; Jupyter and SQL workspaces; developer-services/deployment platform module (these are ordinary lab content later); installing database servers; instructor/college features; arbitrary public repositories as challenges; automated third-party account creation.

### Never in scope

Replacing general-purpose IDEs; running student code with unrestricted privileges; automatic merging of student pull requests; guaranteeing that any third-party service is free or unlimited; guaranteeing AI correctness.

## 1.3 Definitions

| Term | Definition |
|---|---|

## 1.5 Conventions

- **Requirement IDs** are `FR-<AREA>-NNN` (functional) and `NFR-<AREA>-NNN` (non-functional). IDs are never reused. A requirement whose meaning changes receives a new ID; the old one is marked withdrawn in the change log.
- **Verification:** **T** = test (automated or manual with recorded result), **I** = inspection (review of artefact/configuration), **A** = analysis (review of design/threat model/calculation), **D** = demonstration.
- **Test case IDs** are assigned in the Test Plan using the convention `TC-<requirement ID>-<nn>` so each test names exactly the requirement it verifies. Requirements are not mapped to tests by position or by prefix.
- A requirement is **verified** only when a linked test/inspection/analysis/demonstration has an executed, recorded passing result.

## 2.2 User classes

| User class | Description |
|---|---|
| Student | Primary user. Signs in, completes labs, requests AI help, submits work, sees own results. |
| Content author | Team member who authors labs as files and proposes changes by pull request (MVP). |
| Platform operator | Team member who approves content publication, manages roles, performs audited score corrections and operates services. |
| Grader/CI service | System actor. Not an interactive user. |
| External provider | Identity, AI, GitHub or hosting provider accessed through documented interfaces. |

Roles recognised by the backend: `student`, `operator`. Roles are server-controlled claims. Instructor, classroom and institution roles are LATER.

## 2.3 Operating environment

- **Client OS (MVP):** Windows and one of {macOS, Ubuntu LTS}; exact versions and architecture policy are TBD-04. A third OS is R3.
- **Local tools:** Python, `uv`, Git, VS Code (Option A) or the custom shell's dependencies (Option B).
- **Cloud:** managed identity provider (Google sign-in), managed application database, object storage, a small API service, a grader service in an isolated project/environment, secret manager, logging. Specific vendors are TBD-06.
- **GitHub (R3):** platform-owned organisation and GitHub App.

## 2.4 Design and implementation constraints

1. Student code, dependencies, notebooks, project files, archives, AI output and (R3) pull-request content are untrusted input.
2. System changes require explicit consent and shall not need persistent administrator privileges.
3. Protected tests and reference solutions shall never reach a student-controlled environment or AI context.
4. Official scores shall come only from the Grader.
5. No secret shall be shipped in the Client package.
6. The Client UI layer shall not have direct unrestricted shell or filesystem access.
7. Labs are data (manifest, guide, tests); adding a lab shall not require a Client release.
8. Third-party plans, quotas and terms change; lab content referencing them carries a last-verified date.

## 2.5 Assumptions and dependencies

- Students own or may administer their computers and have a modern browser and internet access for sign-in, grading and AI.
- Students create their own third-party accounts and accept third-party terms themselves.
- Cloud AI availability and quality are not guaranteed.
- The MVP is piloted with a small cohort (TBD-10 capacity assumptions).
- Spikes (TBD-01, TBD-02, TBD-03) complete before dependent requirements are finalised.
- Legal review for privacy law and minors (TBD-08) completes before the pilot.

# 3. External Interfaces

## 3.1 User interface

- The Client shall present: lab catalogue, active lab with guide, workspace (editor + terminal), tutor, results/progress and profile.
- The active lab view shall show lab name/version, environment readiness, tutor provider status and result type (Practice or Verified).
- Destructive or privileged actions show an explanation and require confirmation.
- Errors show a plain-language explanation, a recovery action and a diagnostic ID.

## 3.2 Software interfaces

| Interface | Purpose | Constraint |
|---|---|---|
| OS APIs / process spawn | Detect host, spawn tasks | Argument arrays only; least privilege |
| Python tooling (`uv`, `venv`, `pip`, pytest) | Project environments and tests | Locked dependencies |
| Git | Local repository operations | Direct invocation; validated arguments |
| Identity provider | Google sign-in via system browser | Provider-standard flow; no embedded secret |
| Backend API (HTTPS REST/JSON) | Profiles, catalogue, attempts, submissions, scores, tutor proxy | Token validated per request; OpenAPI contract |
| AI provider (via backend proxy) | Tutor | Provider key held by backend only |
| Object storage | Bundles, snapshots | Private; signed or API-mediated access |
| Grader | Verified grading | Isolated; signed results |
| Content repository + CI | Lab authoring and publication | Reviewed changes |
| GitHub App and webhooks (R3) | Template repos, PR/CI/review events | Least privilege; signed webhooks |

## 3.3 Communications

- All network traffic uses TLS with certificate validation.
- Retries apply only to idempotent operations; non-idempotent operations (submission, PR creation) use idempotency keys.
- Offline mode disables or queues operations needing the network and tells the student why.

## 3.4 Hardware

No custom hardware. The Client reads host details (OS, architecture, memory, free disk) only to check prerequisites.

# 4. Primary Use Cases

**UC-01 Complete a Mode 1 lab (MVP).** Student selects lab → environment check → consented setup → workspace opens → follows guide → runs practice checks → asks tutor → submits snapshot → receives Verified result → progress saved. Alternates: setup cancelled; no network; AI unavailable; grader unavailable (submission queued/retry); tests fail (feedback, resubmit).

**UC-02 Publish a lab (MVP).** Author changes lab files → pull request reviewed → CI validates and runs reference solution → operator approves → CI publishes immutable bundle and private protected tests → catalogue shows new version; existing attempts remain pinned.

**UC-03 Fix a bug in an existing codebase (R2).** Student opens challenge → clean workspace at pinned commit → reproduces bug → investigates with tutor → fixes → visible tests → submits → grader runs protected regression tests → feedback.

**UC-04 Practise a pull-request workflow (R3).** Student checks Git readiness → receives per-student template repository → creates branch → implements → pushes → opens PR → CI and trusted grader evaluate the head commit → bot review → points for verified checks; human approval/merge tracked separately.

# 9. Scoring Rules

## 9.1 Principles

1. Only Verified results are official (BR-01).
2. Scores are evidence-based; file existence, self-report and AI output are not evidence of working behaviour (FR-GRADE-018).
3. Rubrics are versioned and visible to the student.
4. Infrastructure errors do not count against the student (FR-GRADE-015).

## 9.2 Mode 1 rubric (default, per-lab configurable)

| Dimension | Weight | Evidence |
|---|---:|---|
| Functional correctness | 50 | Protected and visible tests |
