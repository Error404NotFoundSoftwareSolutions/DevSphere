# 1. Introduction

## 1.1 Purpose and scope

This plan defines how the platform is verified: levels and methods, environments, test data, special suites for the highest-risk areas, entry and exit criteria, and the test cases that trace to each requirement.

**In scope:** all MVP requirements (committed for the pilot), and R2 and R3 requirements (specified now, executed in their releases).
**Out of scope:** requirements tagged LATER. They have no test cases until promoted by change control.

## 1.2 References

`srs_v1.md`, `sad_v1.md`, `idea_v1.md`, `backlog_v1.md`, `tools/gen_rtm.py`, `tools/check_sad.py`.

## 1.3 Defects in test plan v0.2 that this version corrects

| Defect in v0.2 | Correction |
|---|---|
| The traceability matrix paired requirements with test IDs by position, so many pairs did not match in meaning. | Each test names the requirement it verifies (`TC-<requirement ID>-<nn>`). The catalogue is generated from the requirement tables. |
| Counts and coverage claims were typed by hand. | Counts are generated (Section 11). |
| Many cases had no concrete data or expected result. | Section 10 gives inputs and exact expected results for the risky requirements; the catalogue states a pass criterion for every requirement. |
| No tests for hostile or forged grading input, although the product depends on trustworthy scores. | Section 5.1: a hostile-submission suite with named cases. |
| Local test output was treated as authoritative. | Practice results and Verified results are tested separately (FR-GRADE-002, FR-GRADE-003, FR-GRADE-009). |
| Performance and capacity targets had no reference machine or load model. | Section 3.3 and Section 5.6 define them, pending TBD-07 and TBD-10. |
| "Exactly once" synchronisation was tested as if achievable. | Tests check at-least-once delivery with idempotent processing (FR-PROG-004). |

## 1.4 Conventions

- **Test case ID:** `TC-<requirement ID>-<nn>`, for example `TC-FR-GRADE-012-02`. `-01` is the baseline case of a requirement; `-02` and above are additional cases.
- **Method (from the SRS):** T = test, I = inspection, A = analysis, D = demonstration. The method decides what evidence is recorded (Section 2.4).
- **Status values:** Not run, Passed, Failed, Blocked, Exception (approved in writing).
- **Hostile case IDs:** `H-nn` (Section 5.1). **Fixtures:** `FX-nn` (Section 4).

# 2. Test Strategy

## 2.1 Principles

1. **Risk first.** The grader, authentication, secret handling, synchronisation and consented setup are tested most deeply because their failure destroys trust or harms a student's computer.
2. **Lowest level that can prove it.** Logic is proven in unit tests, contracts in integration tests, and only end-to-end behaviour in system tests.
3. **Test the boundary the requirement names.** A rule such as "the Client cannot set a score" is tested at the API with a hand-crafted request, not through the Client UI.
4. **Negative cases are first-class.** Every security and integrity requirement has at least one case that tries to break it.
5. **Reproducible.** Fixtures are versioned; hostile submissions are files in the repository; CI runs the automated suites on every change.
6. **Evidence over assertion.** A pass needs a recorded result (log, report, screenshot or review record).

## 2.2 Levels

| Level | Purpose | Typical tools (suggested; confirm at implementation) | Runs |
|---|---|---|---|
| Unit | Functions and modules (redaction, path validation, manifest validation, scoring maths) | pytest (backend, grader), flutter_test / dart test (desktop app, local worker, packages) | Every commit |
| Integration and contract | Backend with database, storage and queue; API against the OpenAPI contract; Flutter desktop against local worker and mock backend | pytest with test containers, Schemathesis or equivalent, integration_test for Flutter desktop | Every commit |
| System | End-to-end flows on real OSes: sign-in, setup, lab, submit, result | Flutter integration_test runner across Windows, Linux and macOS; manual scripts where automation is impractical | Per sprint, and nightly where automated |
| Security | Authorisation matrix, secret leak, grader hostile suite, dependency scan | Custom suites, secret scanner, dependency scanner, static analysis | Per sprint; hostile suite on every grader change |
| Performance and capacity | Start-up, detection time, grading latency under load | Load tool of choice against a staging grader | Before the pilot and after grader changes |
| Usability and accessibility | Beginner task success, keyboard access, error clarity | Moderated sessions, accessibility checker, checklist | Sprints 4 to 6 and 9 |
| Inspection, analysis, demonstration | Requirements verified by review, calculation or demo | Checklists and review records | When the artefact exists |

# 3. Environments, Tools and Devices

## 3.1 Environments

| Environment | Use | Notes |
|---|---|---|
| Local developer | Unit and fast integration tests | |
| CI | Every commit: unit, integration, contract, dependency scan, content CI | Runs on Windows, Linux and macOS for Flutter desktop |
| Staging (application project) | System tests, performance tests, restore rehearsal | Separate from production; synthetic data only |
| Staging grader (grader project) | Hostile suite, grading load tests | Mirrors production isolation settings; no production secrets |
| Production pilot | Pilot monitoring only | No destructive tests |

## 3.2 Devices

At least one physical machine or clean virtual machine per supported OS (Windows, Linux, macOS; all in MVP), each with a clean image, an image with Python already installed, and an image with an incompatible Python. Reset to the clean snapshot between setup tests.

## 3.3 Reference machine and load model

The reference machine specification is set by TBD-07 and the pilot load by TBD-10. Until closed, the SRS targets are used as proposals: start-up within 10 seconds (NFR-PERF-001), detection within 30 seconds (NFR-PERF-002), and a verified result within 120 seconds at the 95th percentile (NFR-PERF-005). The load model for the grader test uses the TBD-10 cohort size with all students submitting in the same five-minute window.

# 5. Special Suites

## 5.1 Hostile-submission suite for the Grader

Each case is a submission file in the repository, run against a staging grader built exactly like production. **Pass** means the outcome in the last column and no effect outside the sandbox. Any other outcome is a severity-1 defect.

| ID | Attack | Expected outcome | Requirements |
|---|---|---|---|
| H-01 | Fork bomb | Process limit stops it; run marked failed; grader healthy | FR-GRADE-005 |
| H-02 | Memory exhaustion | Killed at the memory limit; run failed; grader healthy | FR-GRADE-005 |
| H-03 | Disk fill in scratch space | Stopped at the disk limit; run failed | FR-GRADE-005 |
| H-04 | Infinite loop | Stopped at wall-clock limit; run failed with timeout reason | FR-GRADE-005, FR-GRADE-015 |
| H-05 | Output flood | Output truncated at the cap; run completes or fails; storage not exhausted | NFR-PERF-007 |
| H-06 | Outbound network connection | Blocked; no connection made | FR-GRADE-005 |
| H-07 | Request to the cloud metadata service and use of any token returned | No token, or a token with no permissions; no object access | NFR-SEC-007 |
| H-08 | Read environment variables and filesystem for secrets and other submissions | Nothing of value found; other submissions not visible | NFR-SEC-007, FR-GRADE-006 |
| H-09 | Write outside the scratch directory | Write denied | FR-GRADE-005 |
| H-10 | Archive with absolute path and `..` entries | Archive rejected before extraction | NFR-SEC-014 |
| H-11 | Archive containing symbolic and hard links to outside files | Links rejected or neutralised; no outside file read | NFR-SEC-014 |
| H-12 | Decompression bomb | Rejected by size and ratio limits | NFR-SEC-014 |
| H-13 | Write a fake passing report file and print pass markers | Run is not marked passed unless the pinned test IDs actually ran and passed | FR-GRADE-021 |
| H-14 | Exit with success before tests run | Run marked blocked (test set mismatch) | FR-GRADE-021 |
| H-15 | Add `conftest.py`, plugins or settings that force all tests to pass | Student test configuration ignored; real results used | FR-GRADE-021 |
| H-16 | Patch the test framework from the submitted package | Detected as mismatch or failure, never passed | FR-GRADE-021 |
| H-17 | Import a package not in the lab's locked set, or try to install one | "Dependency not allowed" result; no download attempted | FR-GRADE-020 |
| H-18 | Signal or kill the parent process, try to reach the Orchestrator | Not possible; run ends normally | NFR-SEC-007 |
| H-19 | Hard-code the visible tests' expected values | Fails protected variants | FR-GRADE-006, FR-BUG-007 (R2) |
| H-20 | Delete or overwrite the tests directory | Tests restored from trusted copy or run marked blocked, never passed | FR-GRADE-021 |

The suite is a gate: it runs on every change to the Grader, its image, its harness or its limits, and before the pilot (FR-GRADE-007).

## 5.2 Secret-leak suite

Plant FX-07 secrets in the workspace, terminal output, a `.env` file, a Git-ignored file and a lab file. Run the full lab flow including tutor requests and a verified submission. **Pass:** the secrets appear in none of: the outbound tutor request seen at the proxy, backend and grader logs, telemetry, crash reports, the submitted snapshot (for default-excluded paths), the evaluation output or the cached bundles (FR-AI-005, FR-GRADE-004, NFR-SEC-005, NFR-PRIV-003). Also search all student-facing API responses and bundles for FX-12 canary strings (NFR-SEC-008, FR-CAT-007).

## 5.3 Token and authorisation matrix

For every protected endpoint, send each FX-08 token and each FX-09 account. **Pass:** only valid tokens succeed; student A cannot read or change student B's data; a student cannot reach operator endpoints; client-supplied role, user ID, score and rubric version are ignored (FR-AUTH-004, FR-AUTH-009, FR-PROF-005, FR-PROF-006, FR-GRADE-009, NFR-SEC-006). The matrix is generated from the OpenAPI document so a new endpoint cannot be forgotten.

## 5.4 Fault-injection suite

Use FX-10 and process kills during: progress sync, snapshot upload, job delivery and result write. **Pass:** no duplicate progress event, submission, result or points; no lost event after reconnect; unfinished work resumes or is reported clearly (FR-PROG-004, FR-GRADE-012, NFR-REL-003).

## 5.5 Tutor policy prompt set

Run FX-13 against a staging proxy and record the model's responses. Two kinds of result are separated:

- **Deterministic (must always pass):** the backend applies the lab's level cap, ignores a higher requested level, treats injected text as data and never grants tools or runs commands (FR-AI-006, FR-AI-009, FR-AI-016).
- **Model behaviour (measured):** the share of answers that respect the level and avoid giving a full solution. The acceptance threshold is a proposal to be set with the product owner; failures are reviewed, not hidden.

## 5.6 Performance and load

Measure start-up and detection on the reference machine (NFR-PERF-001, NFR-PERF-002). Submit the TBD-10 load to the staging grader and record queue time, run time and total at the 95th percentile (NFR-PERF-005), plus cost per submission (NFR-COST-003).

# 6. Process

## 6.1 Entry and exit criteria

| Stage | Entry | Exit |
|---|---|---|
| Sprint | Stories selected; their test cases exist in the catalogue | Every requirement in the sprint's stories has a recorded pass or an approved exception; no open severity-1 or severity-2 defect in those stories; `tools/gen_rtm.py` and `tools/check_sad.py` pass |
| MVP pilot gate | All MVP stories done; spikes closed | SRS Section 10.1 satisfied (Section 7); hostile suite passes; restore rehearsal done; legal and privacy items complete |
| R2, R3 gate | Release stories done | SRS Section 10.2 satisfied (Section 7) |

## 6.2 Defect severity

| Severity | Meaning | Examples | Rule |
|---|---|---|---|
| 1 | Integrity, security or data-loss failure | Grader escape or forged pass; secret leak; one student reads another's data; setup changes a system after consent is declined | Blocks the release; fix and add a regression test |
| 2 | Core flow broken without workaround | Sign-in fails on a supported OS; verified result never returns | Fixed before the sprint closes |
| 3 | Feature degraded with workaround | Wrong message, minor sync delay | Scheduled |
| 4 | Cosmetic | Typo, alignment | Backlog |

## 6.3 Regression and flaky tests

Every fixed defect gets a test. A test that fails intermittently is quarantined within one day, with an owner and a fix date; it is not deleted or silently retried. The CI evidence for FR-CONT-005 uses the same rule for lab tests.

## 6.4 Reporting

Per sprint: requirements verified out of planned, defects opened and closed by severity, flaky tests, automation share, and hostile-suite result. Before the pilot: the generated catalogue shows which requirements still have no recorded pass.

## 6.5 Roles

Developers write unit and integration tests for their stories. A tester (or a developer who did not write the code) owns system, security and usability cases and reviews exceptions. The security reviewer owns the hostile suite and threat-model analysis. The product owner approves exceptions in writing.

# 9. Risks to Testing

| Risk | Effect | Mitigation |
|---|---|---|
| Spikes delay the fixtures that tests need | Tests start late | Build FX-01 and the token matrix in Sprint 0 |
| Desktop test tooling limits what can be automated | More manual system tests | Keep logic in testable packages; use demonstration scripts for UI-only checks |
| Model behaviour is not deterministic | Flaky tutor tests | Separate deterministic policy tests from measured behaviour (Section 5.5) |
| A second OS or hardware is not available | Portability claims untested | Decide TBD-04 early; use cloud VMs for clean-image tests |
| Hostile suite never covers a novel attack | False confidence | Treat residual risk as stated in the SAD; add every real finding as a new H case |
| Real students find issues the plan missed | Late defects | Pilot is monitored and low-stakes; every escaped defect gets a test |

# 12. Change Control

Changes to requirements, fixtures or the hostile suite are made by pull request. After any change to `srs_v1.md`, run `tools/gen_rtm.py`, `tools/check_sad.py` and `tools/gen_test_plan.py`; a new requirement is not accepted until it has a `-01` test case. A withdrawn requirement keeps its test case marked withdrawn.
